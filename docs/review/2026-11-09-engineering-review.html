Dispatch Engineering Review

How Dispatch is built, where it is strong, where it is weak, where it is slow, and what to change first. Five independent read-only reviews by Fable 5.2, joined into one plan.

packages/core: 51,000 lines, 420 test filespackages/web: 47,000 lines396 commits and 57 releases since 26 Oct

Verdict

Dispatch has a strong core idea and some careful engineering: the access gate, the status transaction, limit parking and the backpressure code are good work. The problems come from speed: features shipped in days, on top of a few very large files, with state kept in untyped JSON and in several places at once. Most recurring bugs trace back to four design causes, and each has a clear fix.

Mixed
Daemon architecture
Good status and limits design. One 3,691-line service, an untyped config blob, two composition roots, three copies of the structured transport client.
Mixed
Web client
Shared timeline and good tokens for color. 2,375 inline style objects, no root error boundary, no URL routes on desktop, untyped events.
Weak spots
Performance
Whole-file transcript reads block every thread. The sidebar re-renders on every status event. A 477 KB (gzip) entry bundle. Streaming markdown re-parses at 60 Hz.
Weak spots
Reliability
No record of message delivery, no stall watchdog, status stored in two tables and computed again in the browser. Restart loses PTY, Grok and OpenCode turns.
Mixed
Product
Powerful feature set. Five ways to start a thread, one feature with four names, about 2,900 lines of dead code, and weak navigation for a power user.
Mostly sound
Security
Sound gate, origin and path checks. The risk is in trust boundaries: local callers count as the owner, every thread gets the full Doppler token, plugins are not isolated.

Daemon architecture

One Node process (packages/core) holds Express, three WebSocket servers, SQLite, the PTY manager, three structured transport managers, the MCP tools, the plugin host and twelve timers.

Main runtime flows

A message to a Pretty Claude thread
  1. POST /api/terminals/:id/message → SessionService.sendThreadMessage. The thread spawns again if its process is gone.
  2. The manager writes one JSON line to the CLI's stdin, then parses stdout into a 5,000-event ring.
  3. Four consumers listen: the browser socket, the typed HarnessEvent path into StatusService.accept (one transaction, then broadcasts and coordinator notices), raw listeners in SessionService, and the limit snapshots.
A coordinator starts an agent
  1. The coordinator CLI runs agency-mcp.js as a stdio MCP child; spawn_agent calls the daemon's REST API.
  2. On turn.completed, noteAgentCompletion messages the starter and starts queued dependents.

Strong parts

  • StatusService.accept: one transaction, effects after commit, stale generations and duplicate sequences refused.
  • runtime/adapter.ts: one normalized event contract for all harnesses in 87 lines.
  • limits/: every dependency and the clock injected; wall-clock parks with an attempt cap.
  • Process guards with a crash-loop breaker; only 7 runtime dependencies.

Weak parts

  • SessionService: 3,691 lines, 10+ jobs, 30 optional setters. A missing wire is a silent no-op.
  • Two composition roots. 53 test files use createApp, which has no gate, gauge, parks or PTY wiring.
  • Three copies of the JSON-RPC client, ring trim and turn settle across the structured managers.
  • Harness names compared 38 times in service.ts; 19 folder pairs import each other.

Data layer

  • Three migration styles: CREATE IF NOT EXISTS, 23 ordered steps, and hand-checked columns. The schema is not visible in one place.
  • No index on terminals(session_id), terminals(status), agent_runs(terminal_id) or agent_runs(schedule_id). Archived threads are never deleted, so these tables grow.
  • 294 inline prepare calls; none are cached. lifecycle_events runs a DELETE … NOT IN (… LIMIT 200) on every event.
  • No retention for usage_turns, usage_facts, coordinator_messages, endless_messages, plugin_assist. No synchronous=NORMAL, busy_timeout or checkpoint tuning.

Web client

React, Vite and 38 zustand stores. App.tsx chooses a desktop shell or a phone shell at 768 px. One events socket feeds 12 stores; each open thread has its own socket.

Strong parts

  • One renderTimeline serves threads, the Control Plane and Chat.
  • Phone-only code is about 3% of the client; leaf views are shared.
  • Good color and radius tokens, 10 themes, only 11 hex literals in components.
  • Shared primitives exist: Modal, Select, FilterBar, SwipeRow, SortableList.

Weak parts

  • ChatView.tsx, useStructuredChat.ts and TerminalTab.tsx hold 3,710 lines of the core.
  • 2,375 inline style objects, 439 raw buttons, 22 font sizes, 30 z-index values. No Button, Menu or Popover component.
  • No URL routes on desktop; the phone has its own router. Four "pending intent" fields bridge the two shells.
  • No root error boundary. ServerEvent is { type: string; [k]: unknown }.
  • Modal has no focus trap; only two :focus-visible rules exist.
  • The plugin SDK exposes the raw api object and five stores, so every refactor can break a plugin.

Coherence problems

  • Five things start threads: the user, Chat, the Control Plane, another thread over MCP, and scheduled roles. The Control Plane gets no reports from threads that Chat starts, so you must remember which orchestrator owns which thread.
  • One feature, four names: Control Plane (UI), Overseer (folder and a visible label), coordinator (config), Dispatch tab (code). The name is a setting, but tabs.ts hardcodes "Control Plane".
  • "Agents" means four things: harness defaults, scheduled runs, threads not started by you, and Control Plane workers.
  • Settings sprawl: Skills, Integrations, Secrets, Tools and Plugins are five sections for "what a thread can use".

Performance

Estimates come from the code and the existing build, not from a profiler. Each row says how to measure the change.

Where the time goes

  • Daemon: full-file transcript reads on every page, at every turn end (findNewestUnresolvedUserUuid) and every spawn (16 MB backfill). Each PTY chunk calls every terminal's listener and three scanners. 4 MB of scrollback per terminal, copied three times on attach. A structured ring of 5,000 events that holds every stream delta, so 200 replayed events can be less than one message.
  • Client: entry bundle 1,744 KB raw / 477 KB gzip, only four lazy chunks, no manualChunks. No chat virtualization. Markdown re-parsed in full at about 60 Hz while streaming. Every tab change re-opens a socket and replays up to 4 MB.
  • Network: no compression on API JSON or WebSocket frames. One listTerminals request per project on launch and reconnect. session:tabs-changed sends only an id, so every client fetches the full list again.
  • Sound already: broadcast serializes once, backpressure is careful, assets use brotli and immutable caching, phone resume pings before it reconnects.

Reliability and orchestration

922 commits since 1 September, grouped by subject: report/notice/wake (57, 22 fixes), token/usage/context (65, 19 fixes), status/stuck (38, 13 fixes), resume/restart (20, 10 fixes), history (16, 6 fixes), duplicates (10, 5 fixes).

Six root causes behind the repeat bugs

CauseWhat it produces
A. Derived state in many placesStatus in two tables, the manager's turnOpen and the browser's own fold. Each fix adds one more correction frame.
B. Delivery with no recordA missed edge is lost. Chat already solved this with endless_pending_reports; the coordinator and watch paths do not use it.
C. No stable event id in historyRing, transcript and REST differ per harness, so the client falls back to content fingerprints. Source of the history-loss bugs.
D. Heuristics on third-party CLI outputlooksLikeQuestion, limit banners, transcript tails. The wake-tool list exists twice.
E. The config blob as a state machineNine flags with implied meaning and no transitions, 31 write sites.
F. Recovery per harnessClaude and Codex get a boot kickstart; Grok, OpenCode and PTY threads do not.

Roadmap

Ordered so that each phase makes the next one safer. Phase 1 is all small and independent.

Phase 1 · Quick wins (about 1–2 weeks)
Small, independent, low risk. Each one removes a visible pain.
  • Narrow store updates and memoized rows; composer split; memoized timeline.
  • Compression for JSON and replays; bounded tail reads at turn end and spawn; quieter terminal:activity.
  • Root error boundary; typed server events; delete dead code and unused dependencies.
  • Stall watchdog; orphan-run cleanup at boot; idempotent message POST; watches fire on change only.
  • Block secret reads for no-credential callers; repair network-access.md; re-read index.html when it changes.
  • NodeNext, tests out of dist, ESLint; command palette that opens threads.
Phase 2 · Foundations (about 3–5 weeks)
Changes that remove whole bug classes.
  • Typed thread config and a safe patch store.
  • Async byte-range transcript reader.
  • Delivery outbox and a "why is this thread here" panel.
  • Shared structured-transport core (client, ring, settle).
  • Split the entry bundle; throttled markdown streaming.
  • Attention queue and desktop URL routes.
Phase 3 · Restructure (ongoing)
Larger work, best done after Phase 2 lands.
  • One status authority; a daemon message journal with sequences.
  • buildDaemon() shared by tests; split SessionService into five services.
  • UI primitives and type and space tokens; narrow plugin SDK.
  • One orchestrator model and one set of names (needs your decision); diff review and worktrees per thread.

Method

Five Fable 5.2 reviewers read the repository on 9 November 2026 at the v4.4.1 line, each with one scope: security, daemon architecture, performance, web client and product, reliability and orchestration. All were read-only: no file edits, no daemon, no profiler, no access to ~/.dispatch. Every finding cites a file and line in the source reports. Performance numbers are estimates from code and the existing build, except the 316 ms transcript block, which the repository records itself.

# Dispatch v4.9.3: a thread no longer dies when its saved conversation is gone

## The change

- **A lost Claude conversation now recovers instead of failing.** When the saved conversation behind
  a thread has no transcript on disk, or Claude reports "No conversation found", Dispatch starts a
  new conversation for that thread, delivers your message to it, and tells you in the thread that the
  earlier history could not be loaded. Before, the thread stopped with "Process exited".
  - **Cause:** Dispatch saved the session id when Claude started, before Claude had written anything.
    A thread whose first turn never ran (for example, a process that hung while starting and was
    killed) kept an id that could never be resumed.
  - **Recap:** where Dispatch's own message record holds the earlier messages, the new conversation
    gets a short recap of the latest ones (a gist, not the full history).
  - **Message not lost:** when Claude refuses a resume, the message you sent is sent again to the
    new conversation.
- **A tool server that does not connect is named in the thread.** If Claude reports that an MCP server
  failed to connect or needs sign-in, the thread shows a notice with its name, once.
- **Every Claude thread starts with a 30 second limit for tool servers to connect.** Dispatch sets
  `MCP_TIMEOUT` itself, as inline settings and in the environment, on every Claude thread it starts,
  Pretty or CLI. **Dispatch's value wins over the value in `~/.claude/settings.json`**, because that
  file serves every use of Claude and nobody is watching a thread. One dead server used to hold a thread
  for 5 minutes. To change it, set `DISPATCH_MCP_TIMEOUT_MS` on the daemon.
- **Thread transcripts are kept.** Claude deletes transcripts older than 30 days by default, and any
  claude run can do it, including your own terminal. At start, the daemon adds `cleanupPeriodDays: 3650`
  to your Claude settings file (`~/.claude/settings.json`, or the folder `CLAUDE_CONFIG_DIR` names)
  when that key is not there.
  - A value you set is never changed, and the rest of the file is kept as it is.
  - A file that is not valid JSON is left alone.
  - Threads that Dispatch starts also carry the same value inline.

## Updating

Run `dispatch update`. Threads that are already running pick up the new limits the next time they
start.

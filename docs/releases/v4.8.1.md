# Dispatch v4.8.1 — idle thread processes, data exports and a faster image start on a hosted box

## The change

On a hosted box:

- **Idle thread processes stop, and come back on the next message.** Each open thread kept a CLI
  process until the daemon restarted, so a small host ran out of memory. When the host sets
  `DISPATCH_IDLE_PROCESS_MINUTES`, a thread with no use for that time and no work in flight (no open
  turn, no pending question or approval, no running subagent) has its process stopped. When the host
  sets `DISPATCH_MAX_LIVE_PROCESSES`, a new process start first stops the least recently used idle one;
  a busy one is never stopped. The thread keeps its status and history, and opening it does not start
  the process. The next message resumes the same conversation, the same way as after a restart (about
  0.3 s to the first frame, measured on a laptop).
- **A data export lands in the thread's workspace.** When a company tool answers with an export, the
  daemon downloads the file with the box's own credentials (the thread never sees them), saves it to
  `exports/<name>` in the thread's working folder with a size cap, and tells the agent where it is.
- **The image carries a lazy-loading index (SOCI).** A container platform that supports it can start
  the box before the whole image is pulled. The published digest is the digest of the image index that
  holds the image and the index. Every layer stays gzip.

On your own computer nothing changes: the idle stop and the process cap are off unless the two
variables are set, and the export download needs the platform.

## Updating

A hosted box updates by image. A local install has nothing to do.

# Dispatch v2.8.14 — Update from a non-main checkout fails clearly, not cryptically

## The problem

Updating from a checkout that was sitting on a local feature branch died with a
raw git error:

```
Couldn't update automatically: could not resolve origin/feat/hosted-box-image:
fatal: ambiguous argument 'origin/feat/hosted-box-image': unknown revision …
```

The preflight assumed the current branch had a same-named remote
(`origin/<branch>`). That holds for `main`, but a branch that was never pushed has
no `origin/<branch>` — so the check failed on a message that told you nothing about
what to do. Worse, the suggested fallback (`dispatch update` → `git pull
--ff-only`) fails the same way on such a branch ("no tracking information").

## The fix

The preflight now resolves the branch's **configured upstream** (`@{u}`) instead of
guessing `origin/<branch>` — which is also correct when a branch tracks a
differently-named remote. When there's **no upstream at all**, it says so and tells
you what to do:

> This checkout is on 'feat/hosted-box-image', which has no upstream branch to
> update from — the daemon only auto-updates a branch that tracks a remote
> (normally main). Switch to the release branch with `git checkout main` and
> update, or if you're developing on 'feat/hosted-box-image', bring in the latest
> with `git fetch origin && git merge origin/main` and rebuild.

No behaviour change for a normal install on `main`: `@{u}` resolves to
`origin/main` and the fast-forward check runs exactly as before.

This is a **daemon** change — it takes effect after the update it describes, so the
first update off a feature branch still shows the old message; every one after is
the new, actionable one. Two new tests pin the no-upstream message and prove the
fast-forward check runs against the resolved upstream, not `origin/<branch>`.

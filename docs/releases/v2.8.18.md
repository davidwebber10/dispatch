# Dispatch v2.8.18 — The terminal knows where its history came from

This finishes the history work started in v2.8.17. That release fixed what was
*deleting* content; this one fixes what was *misplacing* it — the scrollback replay
had no idea where in the stream it sat.

## The root problem

A PTY replay was just "the last N bytes, as of right now". The ring buffer tracked a
single `dropped: boolean`, and the scrollback endpoint reported **retained** bytes,
not a lifetime total. So the client could not tell whether a freshly-replayed window
was older than, newer than, or overlapping what it already had on screen — and it
reset the terminal before writing it anyway.

Everything below follows from that one missing number.

## What was going wrong

**Reconnecting collapsed your history.** The replay size was captured once when the
socket was created and reused on every reconnect. On mobile that is 256KB — so a
backgrounded PWA, a screen lock, or a cell handoff quietly rebuilt the terminal from
the last 256KB and discarded the rest.

**Loading older output could give you less.** If the ring had evicted the window you
were reading, "load older" returned a window *newer* than what was on screen. The
client reset and wrote it regardless: you asked for more history and got less, with
the viewport yanked to an unrelated place.

**Loading older output could do nothing at all.** xterm holds 20,000 lines and trims
the head. Once saturated, fetching a bigger replay added no visible history — it was
trimmed straight back off — while still resetting the screen and moving the viewport.

**Replay windows began mid-byte.** The slice was cut at an arbitrary offset, so a
window could start mid-UTF-8 (a replacement glyph) or mid-escape (raw `38;5;226m`
printed as text). Worse, a window starting mid-stream inherited none of the modes set
before it, so a stray "leave alternate screen" inside it could blank the entire
replayed screen at once.

## The fix

The ring now counts evicted bytes and can report the **absolute position** of any
slice it hands out. A new opt-in control frame carries that to the client:

```
?meta=1  →  {"type":"dispatch:replay-meta","startOffset":…,"totalWritten":…,"complete":…}
```

sent once, before the replay bytes. **With the parameter absent the stream is
byte-for-byte what it has always been** — deliberate, so a stale browser tab against
a new daemon can never render JSON into its terminal.

With a position to compare against, the client can finally be conservative:

- a reconnect requests the size it is *currently* showing, not the one it started with;
- a rebuild is refused unless its window is **strictly older** than what is displayed
  (otherwise the current view is kept, and output withheld during the attempt is
  replayed onto it);
- a rebuild is skipped entirely once xterm is at its line cap, instead of pretending
  more history is available.

Slices are also cut on a line boundary now, never inside an escape sequence, and a
window that starts mid-stream is prefixed with a known-state preamble (leave alternate
screen, reset colours, reset scroll region, home) so it renders from a defined state
rather than an inherited one.

## Also fixed: two Pretty-chat bugs

**"Load earlier" could be permanently dead.** When no rendered item carried a real
transcript uuid yet — normal on a streaming thread, where the replay window can hold a
single partial message — paging bailed without touching any state, and nothing that
could re-trigger it ever changed. The guard is correct and stays; it now re-arms the
moment a real anchor appears.

**A message could lose its prose.** If the replay window cut a message after it
started, the replayed deltas were dropped and the reconcile then skipped that
message's text as "already rendered" — so it rendered from neither source. The
reconcile now appends text blocks whose stream never opened, mirroring the rule
already used for tool calls, which recovers the authoritative full text rather than a
mid-sentence tail.

## Activating this

- The Pretty fixes and the client-side terminal fixes are **web-only** — a browser
  refresh, and they apply to existing threads.
- The replay-offset protocol and the slice alignment are **daemon** changes, so they
  need the update to rebuild and restart.

Verified with 42 new tests across daemon and client, each one mutation-checked (the
fix is reverted to confirm the test actually fails without it).

## Known limitation

If a slice is cut inside an OSC sequence whose payload contains a newline (a window
title with an embedded newline, essentially unheard of in agent TUIs), alignment can
still start inside that sequence. Noted rather than fixed.

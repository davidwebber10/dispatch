# Dispatch v3.3.1: Codex threads give back their memory

## The change

- **Ended Codex threads release their tool processes (#99).** All Codex threads share one
  `codex app-server` helper. Each thread starts its own set of tool (MCP) processes inside it,
  and those sets stayed alive after the thread ended. Over a day of Codex threads they piled up
  into thousands of processes and used up a 48GB Mac's memory, which led to a hang and a kernel
  panic. Dispatch now sends `thread/unsubscribe` when a Codex thread ends, and starts the helper
  with `thread_unload_delay_secs=10`, so the ended thread's processes exit about 10 seconds
  later. Thread history is kept. In a live check, process counts went 3, 6, 9, 12, 15 as threads
  opened and back to 3 after they ended.
- **Crash recovery is safer.** If the shared helper dies while a thread is starting or resuming,
  the thread is now retried or resumed by its ID, and stale failure events from a killed or
  replaced session are ignored.

Known limits:
- The 10-second unload delay applies only after the Codex helper restarts, so it takes effect
  after `dispatch update`. Processes already stuck from before the update are freed by that
  restart.
- Reopening a Codex thread from the CLI within the 10-second window was not tested.
- The test helper does not model an unload; only the live check shows it working.
- Grok threads were checked and do not leak.

## Updating

Daemon only. Run `dispatch update`, which restarts the daemon and the Codex helper.

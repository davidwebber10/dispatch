# Dispatch v2.35.1 — queued-delivery turns no longer render twice

## The change

A message sent while a structured thread is mid-turn (the CLI queues it and delivers
it at the next boundary) could render TWICE in the Control Plane stream and ChatView —
and the duplicate survived hard refresh. Fixed.

## Root cause

Right after a process respawn, the daemon's synthetic user echo (uuid-less by design)
lands in the replay ring BEFORE the first uuid'd live event. The first older-history
page then anchors on that later uuid, so the fetched page carries the transcript's
uuid'd copy of the SAME turn. The dedup trusted a real uuid alone — the echo has no
uuid to match — so both copies rendered, and both sources re-served their copy on
every reload.

## Fix

The anonymous-fingerprint dedup is scoped to items rendered before the oldest real
identity (the only geometry that can overlap an older page) and now applies to uuid'd
page items too. Tail echoes stay excluded by construction, so a repeated short turn
("yes") can never delete genuinely-older identical history.

## Updating

**Web-only** — after `dispatch update`, a browser refresh is enough; it also collapses
any duplicate already on screen (the fix acts at render time, no data migration).

# Dispatch v3.4.7: a thread that waits on a finished thread wakes up

## The change

- **Waiting on a thread that already finished now works.** A thread can ask to be woken when
  another thread finishes. Before, the wake only fired if the other thread finished after the
  request. If it had already finished, the waiting thread sat idle until someone noticed.
  Now the request checks first: if the other thread finished during the current turn, the
  result comes back at once.

## What was wrong

PR #104's thread started a Codex reviewer, then ran a long CI watch, then asked to be woken
when the reviewer finished. The reviewer had finished 3.5 minutes earlier, so the wake never
came. #105 fixed a different missed-report case and did not cover this one.

## Under the hood

- Creating a watch now runs a catch-up check. It fires right away, with `firedNow: true`, if
  the target reached the watched state after the waiting thread's current turn started.
  Finishes from before that turn don't count, so old results don't cause false wakes.
- The turn start comes from open usage turns, with lifecycle time as a fallback.
- New tests in core. Reviewed by Opus and Codex over three rounds; both said ship.

## Known limits

- A Codex terminal thread woken this way may stay "waiting" and be skipped.
- A restart or `/clear` can make an old finish look new.
- If the waiting thread asked you a question earlier in its turn, it can miss a finish that
  happened before your answer.
- A message and a watch sent together can run in the wrong order.
- Not yet tested with a real Codex reviewer as the child thread.

## Updating

Needs a daemon rebuild and restart. Run `dispatch update`, then reload the app.

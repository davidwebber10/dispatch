# Dispatch v3.4.5: the sign-in banner's Forward works from a phone

## The change

- **Pasting the callback URL now forwards it.** In the "Authentication required" banner,
  pasting the `localhost…/callback?code=…` address sends it right away. You no longer need
  to tap Forward (Forward and the Return key still work).
- **Failures say why.** If forwarding fails, the banner stays open with a red message, such
  as "That sign-in is no longer waiting on this Mac". You can paste again or open the newest
  sign-in link.
- The button shows "Forwarding…" while it works.

## What was wrong

When you copy the address from Safari, it leaves off the `http://` part, so you get
`localhost:39461/oauth/callback?code=…`. The daemon read `localhost:` as the URL's scheme,
rejected the URL, and the banner threw that error away. Tapping Forward did nothing you
could see. A callback that failed for any other reason (for example, the CLI had restarted)
made the banner disappear without a word.

## Under the hood

- The daemon and the banner both add `http://` to a callback URL that has no scheme.
- A failed forward returns a 400 with a readable reason and leaves the request open. It no
  longer marks the request `error`, which used to hide the banner. If the CLI rejects the
  callback (status 400 or higher), that rejection is reported too.
- New tests: `auth/service.test.ts` (no-scheme URL, refused connection, CLI rejection,
  loopback-only) and two banner tests (forward on paste, error stays visible).

## Updating

Needs a daemon rebuild and restart. Run `dispatch update`, then reload the app.

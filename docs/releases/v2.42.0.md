# Dispatch v2.42.0 — real sign-in checks, doppler secrets in integrations, and a durable aws

Four changes to how threads get CLI tools and secrets. (PRs #57, #58, #59, #60.)

## The change

- **The Tools page checks sign-ins for real.** It runs `gh auth status`, `doppler me`,
  `databricks current-user me`, and `aws sts get-caller-identity` for your AWS profiles, with
  the same environment that a thread gets. A tool shows "installed · authed", "needs auth", or
  a neutral "couldn't check" when a check cannot finish. A "Check again" button and a "checked
  3m ago" line sit beside the title. The CLI-tools note that agents get uses the same result.
- **Integrations can use Doppler secrets.** Write `${NAME}` in a header value or an env value.
  When the MCP server starts, Dispatch reads `NAME` from the Doppler project and config in
  Settings → Secrets, then from the environment. The value goes only into that server's
  environment. It never goes into a command line, a config file, `dispatch.db`, or the
  agent's shell. See `docs/integrations.md`.
- **Such a server's error output goes to a private log:**
  `~/.dispatch/logs/integrations/<name>.<pid>.log` (mode 600). The CLI's own log gets one fixed
  line with the exit code and that path.
- **The Doppler tools keep values out of the transcript.** `doppler_list_secrets` returns names
  only. `doppler_set_secret` and `doppler_delete_secret` return a short confirmation. Errors
  show only the HTTP status and a fixed description. The agent prompt now prefers
  `doppler run -- <command>` and warns against `$NAME` in a command argument.

## What was wrong

- **"Needs auth" was a guess.** The Tools page only looked for variables such as `GH_TOKEN` in
  the daemon's environment. A CLI that signs in through the keychain or a config file (gh,
  databricks, AWS SSO) always showed "needs auth", and agents were told the same.
- **The bundled `aws` broke after a few days.** Its install linked into the macOS temp folder,
  which macOS clears. Then `aws` failed in every thread with "Failed to import encodings
  module", and it hid your own `aws`, because Dispatch's tools folder is first on the thread
  `PATH`.
- **"Secrets come from Doppler" was not true.** Integrations never received Doppler secrets.
- **The Doppler tools returned every secret value** of the config on a list, a set, or a delete.

## Known limits

- `doppler_get_secret` still returns the value to the agent. Prefer `doppler run`.
- `${NAME}` works in a header value or an env value only, not in the URL, the command, or the
  args.

## Under the hood

- `aws` installs under `~/.dispatch/tools/opt/aws`. The recipe downloads next to the old copy,
  tests the new copy with `aws --version`, and swaps by rename, under a lock. An interrupted or
  failed install keeps the old copy.
- A script tool records a fingerprint of its recipe. A changed recipe installs again. Your own
  script tools in `~/.dispatch/tools.json` are recorded, not run again.
- GPT-6 Astra and Claude reviewed all four PRs.

## Updating

Daemon and web app. Run `dispatch update`, then reload the Dispatch tab or the PWA. The first
update downloads the AWS CLI package (about 40 MB) one time. A thread gets the new tool and
integration behavior when it starts, so restart an open thread to use it.

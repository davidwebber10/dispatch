# Dispatch v2.16.1 — Grok is driven like every other harness

## The change

A Grok thread now gets the peer tools — `spawn_agent`, `message_thread`, `report_status` —
and is told what its injected tools are for, the same as a Claude Code or Codex thread.

## What was wrong

v2.16.0 registered Grok's MCP servers but stopped there. Two gaps, both found by asking
whether the harnesses are genuinely treated the same rather than by a test:

**The agent was never told about its tools.** Registering an MCP server hands over the
tools; the system prompt is how an agent learns to reach for them. Grok's builders ignored
`secretsMcp` entirely, so "use Doppler for secrets", the peer-tools prompt and the
tools-awareness note were all dropped. They now ride on `--rules`, Grok's
`--append-system-prompt`, on new, resumed and runner launches alike.

**Grok had no peer tools at all.** `isPeerEligible()` was hardcoded to `claude-code || codex`,
so no agency MCP server was injected. That gate's own comment says it excludes only a plain
shell, "which has no agent process to inject an MCP server or system prompt into" — Grok
plainly has one, so this was an oversight rather than a decision.

The second one mattered more than it looks: without `report_status` a Grok thread could not
declare how its turn ended, which undercut the status hooks shipped an hour earlier.

## Under the hood

`docs/providers.md` gains a table showing all four injections across the three harnesses side
by side, so the next provider has one place to check against. `grok.ts`'s own doc comment
still asserted no hooks and no MCP injection — corrected, with a note that both claims came
from reading `grok --help`, which documents neither.

## Known issue

The core suite fails intermittently when all three packages run concurrently under
`pnpm -r run test` — a different test each time, never reproducible in isolation, and clean
across repeated full runs of core alone (1300/1300). It looks like resource contention rather
than a real defect, and it predates this change. It needs its own investigation.

## Updating

Needs a **daemon rebuild/restart** (`dispatch update`).

# Dispatch v2.8.19 — CLI threads open at the newest output

## The problem

Opening a Codex thread put you at the **top** of its history, so you had to scroll
down to see what the agent had actually just done. Claude threads mostly behaved,
which made it look Codex-specific.

It isn't about Codex. It is about the **transport**:

- A **Pretty** thread has always opened pinned to the bottom — `ChatView` sets
  MessageScroller's `defaultScrollPosition="end"` and adds a post-mount pin that
  holds the bottom through the initial backfill burst.
- A **CLI/PTY** thread had no equivalent. `term.scrollToBottom()` was reachable only
  from the jump-to-latest arrow, so the thread opened wherever xterm's viewport
  happened to land once the replay was written — usually the top.

Codex is **always** PTY, so it hit this on every open. Claude was mostly on the Pretty
transport, which hid it — but a Claude **CLI** thread had exactly the same bug.

## The fix

The first frame of a connection — the replay — now scrolls to the end, through the
same path the jump-to-latest button uses. That matters on mobile: it clears the
inertia/overscroll transforms as well as moving xterm's viewport, rather than leaving
the two disagreeing.

It runs in the **write callback**, because xterm parses asynchronously: scrolling
immediately after `write()` would measure the pre-write buffer and land short of the
end. It re-arms on a reconnect, whose reset is followed by a fresh full replay.

Ordinary live output deliberately does **not** scroll. Pinning every frame would drag
a reader who is scrolled up reading history straight back to the bottom each time the
agent printed a line. The progressive-scrollback rebuild keeps its own anchor restore
and never routes through this path, so the two cannot fight.

## Activating this

Web-only — a browser refresh is enough, and it applies to threads you already have
open. Three tests cover it (open pins, live frames do not, reconnect re-pins), each
mutation-checked.

# Dispatch v4.9.0 — updates only install real releases, and can move you back

## The change

- **Updating now installs only a published release that is on `main`.** Before, the update
  took the highest version tag it could find, even a tag nobody had released. Now the update
  check and the update itself use one rule: the newest published release whose commit is on
  `main`. A stray tag is ignored.
- **If GitHub cannot be reached, the update stops and says so.** It no longer guesses.
- **If you run a version newer than the latest release, Dispatch tells you.** Settings →
  Updates and the update banner say "This version is not a published release" and offer
  **Switch to** the latest release. Before, they said you were up to date, and you stayed
  there for good.
- **Switching back is your choice, and it is safe.** Nothing moves you back by itself. It needs
  a clean working tree and the `main` branch. Your current commit is kept on a backup branch named
  `dispatch-backup/…`, so you can return to it. From a terminal, run
  `dispatch update --switch-back`.
- **A copy that has gone its own way can switch too.** If your copy has commits the latest release
  does not contain (an unreleased branch), the same Switch moves it to the release, with the same
  safety checks. Moving back runs the older version on data the newer one already opened; the app
  keeps its own database tables compatible, so this is safe for ordinary use.
- **If the check cannot tell, it says so.** Settings no longer says "up to date" when GitHub or the
  project's remote could not be read.
- **Version numbers are fixed.** Release 4.7.8 carried 4.7.8 in one file and 4.7.7 in three
  others, so the banner offered it again after you installed it. All four version files now match,
  and a test fails if they ever differ.

## Also in this release: hosted-box features (first published here)

These were built as 4.8.0–4.8.2 on a feature branch and never published. They reach `main` and a
release for the first time in 4.9.0. On your own computer nothing changes.

- **Company models for Claude Code.** On a hosted box, a Claude Code thread can run on a company
  model the platform grants (first: `claude-opus-5-5`), with no personal Claude login needed. The box
  token and model credential never reach the thread. A model that is not granted is refused. New
  capability `company-claude-v1`. The forced-login setting moves to a drop-in file that the daemon lifts
  only for a person granted a company model.
- **Idle thread processes stop and come back on the next message,** when the host sets
  `DISPATCH_IDLE_PROCESS_MINUTES` or `DISPATCH_MAX_LIVE_PROCESSES`.
- **A company-data export lands in the thread's workspace** under `exports/<name>`.
- **The hosted image carries a lazy-loading index (SOCI)** so a box can start before the full pull.

## If you are stuck on an unreleased version (4.8.x)

An older updater cannot take you back by itself: it tries to fast-forward and says your copy has
diverged. Move once by hand, from the Dispatch folder on the `main` branch, with a clean working tree:

```
git fetch origin
git branch dispatch-backup/before-4.9.0
git switch main
git reset --hard v4.9.0
dispatch build
dispatch restart
```

The `dispatch-backup/before-4.9.0` branch keeps the commit you were on. From 4.9.0 on, Dispatch
offers the switch itself.

## What was wrong

On 13 November an update took an unreleased 4.8.0 tag from a feature branch. A copy that runs a
version above the newest release said "up to date", so it never came back. The check and the
update followed different rules; now they share one.

## Under the hood

- One shared function picks the target. The two copies of the old tag-picking code are gone.
- `dispatch update` fast-forwards to the release's commit, not to a tag name.
- A dev checkout of `main` a few commits past the latest release, with the same version, is not
  treated as ahead.

## Updating

Run `dispatch update`, then reload the app. Daemon rebuild and restart: yes.

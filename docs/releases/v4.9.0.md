# Dispatch v4.9.0 — updates only install real releases, and can move you back

## The change

- **Updating now installs only a published release that is on `main`.** Before, the update
  took the highest version tag it could find, even a tag nobody had released. Now the update
  check and the update itself use one rule: the newest published release whose commit is on
  `main`. A stray tag is ignored.
- **If GitHub cannot be reached, the update stops and says so.** It no longer guesses.
- **If you run a version newer than the latest release, Dispatch tells you.** Settings →
  Updates and the update banner say "This version is not a published release" and offer
  **Switch to** the latest release. Before, they said you were up to date, and you stayed
  there for good.
- **Switching back is your choice, and it is safe.** Nothing moves you back by itself. It needs
  a clean working tree and the `main` branch. Your current commit is kept on a backup branch named
  `dispatch-backup/…`, so you can return to it. From a terminal, run
  `dispatch update --switch-back`.
- **Version numbers are fixed.** Release 4.7.8 carried 4.7.8 in one file and 4.7.7 in three
  others, so the banner offered it again after you installed it. All four version files now match,
  and a test fails if they ever differ.

## What was wrong

On 13 November an update took an unreleased 4.8.0 tag from a feature branch. A copy that runs a
version above the newest release said "up to date", so it never came back. The check and the
update followed different rules; now they share one.

## Under the hood

- One shared function picks the target. The two copies of the old tag-picking code are gone.
- `dispatch update` fast-forwards to the release's commit, not to a tag name.
- A dev checkout of `main` a few commits past the latest release, with the same version, is not
  treated as ahead.

## Updating

Run `dispatch update`, then reload the app. Daemon rebuild and restart: yes.

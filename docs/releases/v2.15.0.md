# Dispatch v2.15.0 — a Grok thread survives a daemon restart

## The change

Grok threads now resume. Restart the daemon, relaunch the thread, and it picks up the same
conversation instead of quietly starting a new one.

## What was wrong

Nothing captured Grok's session id, so a thread had nothing to resume into. The failure was
silent: the thread came back looking fine, with none of its history.

## Under the hood

Grok is the first provider that lets Dispatch **name** the session rather than discover it.
`--session-id <uuid>` takes a fresh v4 uuid at spawn, and it is stored as soon as the process
is alive.

That is a better position than the other two. Claude Code and Codex both have to find the id
*after* the fact by polling the filesystem — a poll that can miss, and which needs an
ambiguity heuristic for the case where two sessions are born in the same window. Assigning
the id has neither problem.

`SessionProvider` gained `assignsSessionId` to mark which path a provider takes, so the
existing discover path is untouched for Claude and Codex.

Two details that matter:

- The id is stored **after** the pid, never before. A stored id for a process that failed to
  start would send the next relaunch chasing a conversation that never existed.
- `--session-id` is kept off resumes. For Grok it names a *new* conversation, and passing it
  while resuming forks instead of resuming.

Browsing prior Grok sessions in the New Thread modal is still absent — `grok sessions list`
prints human text with no JSON flag. That is a separate piece of work.

## Updating

Needs a **daemon rebuild/restart** (`dispatch update`).

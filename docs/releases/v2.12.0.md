# Dispatch v2.12.0 — Grok, and a New Thread modal that fits it

## The change

**Grok is a harness.** xAI's Grok Build CLI joins Claude Code, Codex and Terminal in the New
Thread modal, driven the same way the others are — spawned as you, in a managed terminal.

**The modal was rebuilt to hold four of them.**

- **Name comes first.** It is the one field you always fill in, and it takes focus.
- **Four harnesses across one row**, instead of a three-column grid with an orphan.
- **Mode and Model share a line.** Model is a picker now rather than chips, so a provider's
  list can grow without wrapping. Five stacked option groups became three — the modal is
  *shorter* with four harnesses than it used to be with three.
- **Auto-archive folds behind Advanced**, where a set-once control belongs.

**A harness whose CLI isn't installed is greyed out and inert**, with the reason spelled out
and an **Install** button beside it that runs that vendor's own one-liner on the machine
running Dispatch. This applies to Claude Code and Codex too, not just Grok. The Setup wizard
gains the same button.

Installing does not sign you in — no CLI's login can be automated — so an installed-but-signed-
out harness stays selectable and tells you the one command to run. A CLI thread will also
prompt you inline.

## What was wrong

Nothing was broken; the picker simply had no room. The grid was `repeat(3, 1fr)`, so a fourth
card wrapped onto its own row at one-third width, on a modal that already scrolled on a phone.

## Under the hood

Grok's flags were read from `grok --help` on **1.0.3**, not from documentation — several
third-party guides describe a `--yolo` flag that does not exist. The real autonomy flag is
`--permission-mode bypassPermissions`.

Provider detection now covers all three CLIs and probes each installer's own paths
(`~/.grok/bin`, `~/.local/bin`) as well as `PATH`. That matters: the daemon resolves the login
shell's `PATH` once at startup, so a CLI installed by the new button would otherwise stay
invisible until a restart.

`POST /api/setup/install/:provider` runs the install. The provider name is checked against a
fixed allow-list *before* it selects a constant command, so nothing from a request reaches the
shell. Success is judged by re-detecting the binary afterwards, not by the installer's exit
code — an installer can exit 0 having put the binary somewhere the daemon cannot see.

Grok deliberately ships without Pretty mode, a resume list, Doppler MCP injection, or status
hooks. `docs/providers.md` explains each gap and what closing it would take. Pretty is the
interesting one: `grok agent stdio` speaks ACP, so it is buildable — the same project Codex
Pretty was.

New tests: `grok.test.ts`, `setup/install.test.ts`, `routes/setup-install.test.ts` (core), and
eleven new cases in `NewThreadModal.test.tsx` covering Grok, the disabled state and install.

## Updating

Needs a **daemon rebuild/restart** (`dispatch update`). The modal is web, but the provider,
the detection and the install endpoint are all in core.

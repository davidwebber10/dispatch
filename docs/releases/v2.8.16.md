# Dispatch v2.8.16 — Codex threads launch with full permissions

## The problem

A Codex thread opened interactively (a normal Codex thread / PTY) launched with
Codex's **default** approval policy and sandbox — so it stopped and waited for
approval on commands instead of running autonomously.

Claude threads never have this problem: `buildNewCommand` / `buildResumeCommand`
always prepend `--dangerously-skip-permissions`. Codex had the equivalent flag on
its `exec` **runner** path (spawned agents), but **not** on the interactive
new/resume launches — so those two paths ran un-bypassed.

## The fix

Both `buildNewCommand` and `buildResumeCommand` now prepend
`--dangerously-bypass-approvals-and-sandbox` — Codex's analogue of Claude's flag:
it skips every approval prompt *and* drops the sandbox, so the thread runs fully
autonomously. It's a global flag (verified via `codex --help` / `codex resume
--help`), so it precedes the `resume` subcommand just like the `-c` overrides.

The flag is now a single shared `FULL_PERMISSIONS` constant used by new, resume, and
the exec runner alike, so the three Codex launch paths can't drift apart again.

## Scope

- Applies to **interactive / PTY** Codex threads — the ones that were stalling.
- Codex **Pretty** (structured) threads were unaffected: they run through the
  auto-approve membrane in `CodexStructuredSessionManager` (the same design Claude's
  Pretty threads use), not the CLI's launch flags.

This is a **daemon** change — it takes effect for Codex threads started after the
daemon updates to 2.8.16; a thread already running keeps the launch it booted with.
Two provider tests pin the flag on the new and resume commands.

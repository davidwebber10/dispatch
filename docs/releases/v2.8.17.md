# Dispatch v2.8.17 — History stops skipping lines; threads can message a CLI peer

Three fixes: two for history that was silently losing content, one for thread-to-thread
messaging.

## 1. Pretty history was deleting a quarter of itself when you scrolled back

Paging back through a Pretty thread dropped messages outright — turns simply absent,
tool cards stuck on `running…` (their result deleted), stray `Output · N lines` rows
(their call deleted).

`loadOlder` deduped each incoming page against a **content fingerprint**
(kind + tool + text) built from *every* item already on screen — and applied it even
to items carrying a brand-new transcript **uuid**. A uuid proves an item is a
different message, so this deleted genuinely distinct history purely for repeating
content. That is routine in a coding session: the same `Edit` result, a re-run
command, two empty tool outputs, a repeated short user turn.

Measured against three real transcripts, it discarded **27%, 30% and 26%** of paged
items (851 / 665 / 433 visible messages). It also compounded — the comparison set
grows with every page, so scrolling further back deleted more.

The fingerprint is now the *fallback* its own comment always described: built only
from rendered items with no real identity (the client's optimistic echo, a mid-stream
synthetic block) and applied only to incoming items that likewise lack one. A real
uuid decides identity by itself.

Both existing dedup tests passed for the wrong reason — their "duplicate" shared a
uuid, so the broken branch never ran. The case none of them covered (distinct uuids,
identical content) is now pinned.

## 2. PTY rebuilds duplicated, then lost, terminal output

During a progressive-scrollback rebuild the old and the new socket are both subscribed
to the same PTY, so every chunk arrives **twice** — and both copies went into one
shared buffer. Two failures fell out:

- **On success, every mid-rebuild chunk was written twice.** Duplicated raw PTY bytes
  are not harmless: a doubled cursor-up or scroll-region escape moves the cursor twice
  as far, so following output overwrites lines that should have survived — which reads
  as lines disappearing.
- **On abort, the whole buffer was discarded.** The old view is never reset on abort
  and nothing replays afterwards, so up to 10 seconds of output was permanently gone.

The buffer is now kept per socket, and each outcome drains the one contiguous with the
view it keeps: success drains the new socket's frames; a failed rebuild replays the old
socket's withheld frames onto its still-intact view. Reset-driven and unmount aborts
deliberately recover nothing — a full replay is already inbound, or the terminal is
going away.

## 3. A thread could only message a peer that was in Pretty mode

`message_thread` posted to a route that called the structured-transport send directly,
which throws `no structured session for terminal` for a CLI/PTY thread. *Reading* a PTY
peer always worked (it reads the on-disk transcript) — only sending was broken.

Messaging is now transport-agnostic: a Pretty thread keeps its structured channel; a
CLI/PTY thread has the message typed into the TUI it is already drawing. Multi-line
text is delivered as a **bracketed paste** so the TUI takes it as one block — a bare
newline would submit a half-written message on every line. (Verified against a real
Claude Code TUI that it enables bracketed paste.) Images can't be typed into a
terminal, so they're reported as dropped rather than silently delivering half a
message, and an image-only payload is refused.

## Activating this

- Fixes **1 and 2 are web-only** — a browser refresh is enough, and they repair
  **existing** threads, not just new ones.
- Fix **3 is a daemon change** — it needs the update to rebuild and restart.

## Known, not fixed here

Three further history issues are understood but deferred: the load-older anchor math
versus xterm's 20,000-line cap (on long sessions, loading older adds no visible
history); a "Load earlier" button that can go permanently dead when no rendered item
carries a real uuid yet; and the structural one — the scrollback replay protocol
carries no position information, so the client cannot tell whether a new window is
older, newer, or disjoint from what it already shows, yet resets before writing it.
That last one needs a protocol change and is the biggest remaining win for PTY history.

# Dispatch v2.12.1 — browser sign-in reaches your phone again

## The change

A CLI in a thread that needs a browser login now surfaces its sign-in URL in the
**Authentication required** banner, so you can complete it on your phone and paste the
callback back. That was always the design; it had stopped working entirely.

Three ways a CLI can ask for a browser are now caught, where before only one was attempted:

- **`$BROWSER`** — the original shim.
- **`open` / `xdg-open`** — shadowed on `PATH`. Most macOS CLIs call the platform opener
  directly and ignore `$BROWSER`. The shims relay only `http(s)` URLs and hand everything
  else to the real binary, so `open .` and `open -a Xcode file.swift` are untouched.
- **A URL the CLI merely prints** — the thread's output is scanned. Device-code grants exec
  nothing at all, so this is the only way they can ever be caught.

## What was wrong

The relay was dead, and silently so.

The spawn environment is merged from three contributors — secrets, bundled tools, and the
browser shim — and each builds `PATH` by prefixing `process.env.PATH`. Merged with object
spread, the last one won and the others' prefixes vanished. So `$BROWSER=dispatch-open` was
set correctly while `dispatch-open` was not on `PATH` at all: every CLI that honoured the
convention got "command not found", and the shim swallows errors by design, so nothing was
ever shown.

Fixing that alone would still have missed most real logins. Measured against a real PTY,
`gh auth login --web` never invokes `$BROWSER` in any configuration — despite the flag name
it is a device-code grant that prints a code and a URL and polls in the background.

## Under the hood

Two hazards in output scanning, both found by running it against a real terminal rather than
in tests:

- A terminal hard-wraps a long URL at its width with no space. Lines of at least 60
  characters are rejoined; shorter ones are real line breaks, so `…/login/device` followed by
  `Enter code` never becomes `…/login/deviceEnter`. Same class of bug as the wrapped login
  token in `0138bf0`.
- A URL sitting at the end of the buffer may still be arriving, and was being reported twice
  — once truncated with zsh's `%` prompt marker glued on, once complete.

Detection is deliberately narrow: `https` only, never loopback, and the URL must carry an
unmistakable sign-in signal. Ordinary links an agent prints are ignored. One report per URL
per terminal, ten distinct URLs at most.

New: `docs/browser-auth-relay.md` documents the whole loop, all three triggers, and the
`PATH` rule any future contributor to the spawn environment has to follow.

New tests: `auth/url-detect.test.ts` (25 cases) and four more in `auth/shim.test.ts`.

## Updating

Needs a **daemon rebuild/restart** (`dispatch update`) — all of it is in core, and the shims
are written at daemon startup.

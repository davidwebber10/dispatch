# Dispatch v2.16.0 — Grok reports status, and gets your secrets

## The change

Grok threads now show working/idle like Claude Code and Codex do — the spinner, the status
dot, the board columns — instead of guessing from terminal timing. They also get the Doppler
secrets MCP server, so a Grok agent can fetch and store secrets like the others.

## What was wrong

Both were listed as limitations when Grok shipped in v2.12.0, and **both claims were wrong**.

Grok's binary carries Claude Code's entire hook vocabulary — `Stop`, `PreToolUse`,
`PostToolUse`, `SubagentStop`, `Idle`, `SessionStart`, `SessionEnd`, `Notification`,
`UserPromptSubmit`, `PreCompact` — and it reads Claude Code plugin layouts, including
`hooks/hooks.json` and `.mcp.json`. I checked the top-level `--help`, saw no `notify`
equivalent, and concluded too quickly.

## Under the hood

One generated directory per spawn, handed over with `--plugin-dir`, carries both injections:

```
.mcp.json          the same MCP servers Claude gets
hooks/hooks.json   lifecycle hooks, in Claude's own schema
```

Grok documents that flag as the highest-priority, always-trusted scope, *"used by the Agent
SDKs to inject per-connection plugins"* — so nothing stalls on a trust prompt and the user's
own config is never touched. The directory is rewritten on every spawn, and a file for an
injection this spawn does not want is removed rather than left behind.

`statusStrategy` moves from `pty-timing` to `hooks`. The events route and the status service
needed **no changes at all**: `ingest()` sends anything that is not `codex` through
`normalizeClaude`, and Grok's payloads already use Claude's schema.

Hooks are `type: "command"` running `scripts/grok-hook.mjs`, which forwards the stdin payload
to the events route. Grok documents only that hook type, so a helper works whichever
transports a given build supports — the same approach the Codex notify helper takes.

Resumes carry the plugin dir too. Without that a resumed thread would come back mute.

## Also

The core test timeout moves off vitest's 5-second default. Route suites doing real sqlite and
process work were crossing it under parallel load and failing a different test on each run at
about 5003ms. The tests were never wrong; the budget was too tight on a contended machine.

## Updating

Needs a **daemon rebuild/restart** (`dispatch update`).

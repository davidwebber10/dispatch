# Dispatch v4.13.2: the update works on any Node, and the phone sees new projects

## The change

- **`dispatch update` no longer fails on the wrong Node.** The updater now builds with the Node your daemon was installed with. It does not use the Node your shell happens to pick.
- **Dispatch now says it needs Node 22.13 or newer.** The `.nvmrc` said 20, so a shell that reads it (fnm, nvm) ran Node 20 in the repo. The update then stopped with `No such built-in module: node:sqlite`.
- **The build rebuilds native modules.** `better-sqlite3` is rebuilt under the daemon's Node, so it loads after the restart.
- **The build stops with a plain message** when the daemon's Node is missing or too old. It does not carry on with a different one.
- **The phone sees new projects.** A project created while the phone was away now shows up when it reconnects. A project list that failed to load at launch retries on the first connection.

## One-time recovery for an install stuck on the old updater

An install that still runs the old updater needs one manual step. Use the Node your daemon was installed with. Replace `24` with its major version. Run these from the Dispatch checkout.

If `dispatch update` fails before it pulls anything:

```bash
fnm exec --using 24 ./bin/dispatch update
```

If the pull already happened and the build failed:

```bash
fnm exec --using 24 ./bin/dispatch build
fnm exec --using 24 ./bin/dispatch restart
```

Without fnm, put that Node first on PATH for the same commands. After this, plain `dispatch update` works from any shell.

If `dispatch build` stops with a message about the daemon's node, that Node is missing or older than 22.13. Install a working one. Then run `dispatch install`, `dispatch build` and `dispatch restart` under it.

The full steps are in `docs/node-version-recovery.md`.

## Install

This needs a daemon rebuild and restart (`dispatch update`). A browser refresh is not enough.

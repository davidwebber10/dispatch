# Dispatch v2.17.1 — Grok threads start again

## What was wrong

Every Grok thread failed to launch:

```
error: unexpected argument '--plugin-dir' found
Usage: grok --permission-mode <MODE> [PROMPT]
```

`--plugin-dir` exists only on the `grok agent` **subcommand**. The PTY runs the top-level
`grok`, which rejects it outright. I read the flag from `grok agent --help` and assumed it
was global — the same class of mistake as reading the top-level help and concluding Grok had
no hooks at all.

Grok has been broken since v2.16.0. If you are on 2.16.0 or 2.17.0, this is the fix.

## The change

Hooks and MCP servers now reach the CLI through a **per-thread `GROK_HOME`**, the documented
way to point Grok at a different config directory. The plugin content was never the problem —
only how it was delivered.

Everything in the per-thread home except `plugins` is symlinked back to the real `~/.grok`,
so the thread keeps your credentials, your `config.toml`, and one shared session store. Only
`plugins` is genuinely per-thread: sharing it would make every thread load every other
thread's hooks and report status for the wrong terminal.

## How it was verified this time

By launching it. The real CLI, with the exact argv the provider builds, under a real PTY: no
startup error, the TUI comes up. `grok inspect` confirms the plugin is discovered —
`dispatch (user, enabled)  hooks, 1 MCPs`.

That check is exactly what was missing when v2.16.0 shipped. Unit tests asserted the flag was
present in the argv; none of them asked whether Grok accepts it.

A new test now asserts every flag the provider emits is one that `grok --help` lists, so a
flag borrowed from a subcommand fails in CI instead of at launch.

## Updating

Needs a **daemon rebuild/restart** (`dispatch update`).

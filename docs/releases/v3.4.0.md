# Dispatch v3.4.0: security fix, other devices now need to sign in

**Please update now.** Before this release, any device on the same network as your computer
(a coffee shop, hotel or office guest Wi-Fi) could open Dispatch and run commands as you. A web
page you visited could also connect to it. This release closes both (#94, #102).

## What you will notice

- **On the computer that runs Dispatch, nothing changes.** No sign-in. The same holds for agents,
  hooks, MCP tools and the `dispatch` command.
- **Windows (WSL2):** a Windows browser at `localhost` needs no sign-in.
- **Your own Tailscale devices need no sign-in.** That covers direct use
  (`http://MACHINE.ts.net:3456`) and `tailscale serve` (the HTTPS address, including the phone app).
  Only devices on your own Tailscale account count. A coworker on a shared tailnet, or a device
  shared in from another tailnet, is treated as any other device.
- **Any other device sees a "not signed in" page.** That means another laptop on the same Wi-Fi, a
  public tunnel, or `tailscale funnel`. On the computer that runs Dispatch, run `dispatch access` to
  get the access token, then paste it into the page once per browser. For a phone,
  `dispatch access --link HOST` prints a link that signs in directly.
- **Web pages on other sites can no longer drive Dispatch.** Requests from a foreign origin are
  refused, WebSockets included, and so are cross-site requests. Other sites also cannot frame
  Dispatch.
- **Scripts that call the API from another computer now get `401`.** Send
  `Authorization: Bearer TOKEN`, and read the token from `~/.dispatch/access-token` rather than
  typing it on a command line.
- **There is no switch to turn this off.**

## Other changes

- `dispatch access` prints the token. `rotate` makes a new one and signs out every device.
  `allow-host NAME`, `remove-host NAME` and `list-hosts` manage extra names that count as this
  computer, for example the public name of a proxy that has its own sign-in.
- `dispatch status` and the start-up log say that other devices need the token. They never print it.
- The data folder `~/.dispatch` is now readable only by you (`0700`). The database and the token
  file are `0600`, so other accounts on the same computer cannot read them.
- Dispatch sends `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff` and a same-origin
  referrer policy on every response.
- Behind another proxy or tunnel (Cloudflare or similar), people see the sign-in page. Sign in once
  per browser, or run `dispatch access allow-host YOUR.HOSTNAME` once. See `docs/network-access.md`.

## Known items

- A proxy on the same computer that adds no forwarding headers, or that passes a client's own
  `X-Forwarded-For` through unchanged, looks like `tailscale serve` or the computer itself. Give
  such a proxy its own sign-in, or do not use it. This is an accepted limit (R-6 in the design).
- On Windows, a `netsh interface portproxy` rule that exposes Dispatch to your network is not
  protected. Remove it and use Tailscale.
- Other accounts on the same computer can still reach Dispatch over loopback. Agents run as you and
  can read the token file.
- Not yet tested on real WSL2 hardware (NAT and mirrored mode, `tailscaled` inside WSL), or from a
  second Tailscale account. Both are follow-ups after this release.
- `X-Frame-Options: DENY` also stops Dispatch showing itself inside its own Browser tab.
- Behind a proxy that hides client addresses, one visitor's failed sign-ins can delay another
  sign-in for a minute.

## Updating

Run `dispatch update`, then reload the app. After the update, a browser on another device shows the
sign-in page once. Full details: `docs/network-access.md`.

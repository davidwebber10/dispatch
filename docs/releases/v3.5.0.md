# Dispatch v3.5.0: every thread gets its own key

## The change

- **Each thread, Chat turn and shell tab now has its own secret key.** The key is made when
  the thread starts. The daemon reads who is calling from the key and applies rules for it:
  - A worker thread can only act in its own project.
  - A thread cannot pose as the owner or call owner-only routes (for example secrets and
    usage limits). Those calls get `403 owner_only`.
  - A coordinator (overseer) can also read threads in any project, and can message other
    projects' overseers, up to 10 messages an hour. Each such message starts with a line
    naming the sender.
- **Nothing changes for you.** Calls with no key keep working as before. They are only
  counted, and `dispatch status` shows the counts.
- **Keys never land in logs or transcripts.** Keys are redacted from scheduled-run output,
  Chat, status reports, notices, conversation views and daemon logs.

## Restarts

Keys live only in memory. A daemon restart revokes every key, and each thread gets a new one
when it wakes. Tested on an isolated copy: clean stop, `kill -9`, Codex crash and quick
restart, every thread type, a coordinator with a worker, queued, role and scheduled runs,
Chat, usage-limit wake (#106) and model relaunch (#108). After the catch-up with v3.4.7, the
wake cases were checked again, including the #109 missed-wake fix.

## Known limits

- **Background jobs started before an update are refused after it.** A `nohup` job still
  holding an old key gets 401 once the daemon restarts. Run `dispatch update` when no long
  background jobs are running.
- A Codex Pretty thread keeps one key for its whole life on this daemon. A detached job from a
  stopped Codex Pretty thread keeps working until the thread is archived or the daemon
  restarts.
- The Grok CLI view does not load Dispatch tools. Grok model calls after a restart were not
  tested (quota).
- A project relaunched the old way (no terminal rows) runs with no key, as before.
- The hosted box is covered by unit tests only.
- The full every-thread-type restart and `kill -9` test ran before the last catch-up with
  main; after it, only the wake cases were rerun.
- Minor: in a thread, a blank `PORT` skips the CLI's port-mismatch message. Requests still go
  only to `DISPATCH_API`.

## Rollback

Install v3.4.7 again. There is no database change.

## Updating

Needs a daemon rebuild and restart. Run `dispatch update` when threads are idle, then reload
the app.

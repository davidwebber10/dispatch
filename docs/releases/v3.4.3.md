# Dispatch v3.4.3: limit auto-resume, model choices stick

A fix release (#106, #108). Nothing to set up.

## What you will notice

- **Threads that hit a usage limit wake themselves.** When a Claude Code or Codex thread stops on
  a session, weekly or Fable limit, it shows "Paused: session limit, resumes ..." and sends itself
  "continue" about 90 seconds after the reset. Wakes are staggered. A thread you messaged,
  stopped or archived in the meantime is left alone. After 5 failed wakes it stops and says so.
  Pauses survive a daemon restart.
- **Model and effort changes stick.** If you change a thread's model or effort inside the thread
  (`/model`, `/effort`), a later relaunch (for example a CLI/Pretty switch) keeps that choice
  instead of going back to the thread's original model.
- **Every open device follows a CLI/Pretty switch.** Before, a phone that had reconnected could
  stay on the old mode until the app was closed and reopened.

## Cause

- Limits: nothing detected a limit stop, so a thread that hit one sat idle until someone noticed.
- Model: the relaunch used the model saved when the thread started. A change made inside the
  thread lived only in the running process.
- Phone: when the app swapped its live connection, the old one was never marked closed, so a
  switch missed during the swap was never fetched again.

## Known items

- Checked with automated tests. Not yet run on a real phone or a real limit stop. A Fable-limit
  stop is unproven live.
- A reset time that names a weekday or a different year can be read wrong in the pause banner.
- Grok and opencode threads, API-key logins and paid overage are not handled by auto-resume.
- A model or effort change made right before a relaunch, with no reply in between, is not kept.
  A pick of an older model in the same family is saved as that family's newest.
- Threads with a fixed role keep their role's model.

## Updating

Run `dispatch update`, then reload the app.

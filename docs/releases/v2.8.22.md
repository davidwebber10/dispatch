# Dispatch v2.8.22 — Codex threads can load their history in Pretty

## The problem

In a Codex thread on the Pretty transport, the **Load earlier** button did nothing. It
stayed on screen and never fetched anything, however many times you pressed it.

## The cause

Two independent faults, and fixing either alone would not have helped.

**1. The button could not start a fetch.** `loadOlder()` anchors its first page on a
Claude Code transcript `uuid`:

```ts
itemsRef.current.find((it) => it.uuid && !it.uuid.startsWith('s-'))?.uuid
```

`codex-translate.ts` never assigns a `uuid` — there are zero occurrences in the file — so
that anchor was always `undefined` and the guard below it returned without fetching,
changing no state. `hasMore` stayed optimistically `true`, so the button stayed visible.
The re-arm flag only fires when a real uuid arrives, which for Codex never happens.

**2. There was no data behind the button.** `getConversation` refused every thread that
was not `claude-code` and answered `{ items: [], hasMore: false, unsupported: true }`.
Codex keeps its history in `~/.codex/sessions/<Y>/<M>/<D>/rollout-<ts>-<sessionId>.jsonl`,
and nothing read it. The web client declares `unsupported` in its types but never reads it.

## The fix

### Reading the rollout transcript

`conversation/codex-transcript.ts` parses a rollout line into the same `ConvItem` the
Claude parser produces. Two families of line are skipped deliberately:

| Skipped | Why |
| --- | --- |
| `event_msg/*` | The UI event stream **duplicates** `response_item`. A sampled transcript held 179 `event_msg/agent_message` against exactly 179 assistant messages — the same turns twice. |
| `reasoning` | The text is in `encrypted_content`; `summary` was empty on all 1553 reasoning lines. Nothing readable. |
| `response_item/agent_message` | Inter-agent traffic, not the assistant. Its 146 lines match the 146 `inter_agent_communication_metadata` lines one for one. |

`findCodexRolloutPath` locates a rollout by session id — the caller knows only the id and
Codex files by date, so the tree is searched. Hits are cached; misses are not, since a
young session's file may not exist yet.

### Removing the overlap instead of deduping it

The ring **also** holds a copy of that history, backfilled on every resume. Simply letting
the client fetch the newest window would have overlapped the replay, and dedup then falls
back to a content fingerprint. The socket items come from `codex-translate` and the REST
items from the rollout parser, and **the two do not agree on tool calls** — which are 1143
of the 2547 items in a real thread. That would have duplicated 45% of the transcript.

So the overlap is removed rather than reconciled: **a Codex thread's history now comes from
REST, and its socket carries only live turns.** `historyOwnedByRest` is true for Codex
only; Claude Code keeps replaying its ring, where per-message uuids make the overlap safe
and the path is the fast, well-covered one.

The mechanism reuses what already existed: replaying no events makes `hasRenderableEvents`
false, which fires the `system/inactive` sentinel, which is already the signal that tells
the client to hydrate from REST and set its paging anchor.

## Verification

Verified end-to-end against a real 6996-line rollout, through the HTTP endpoint, on an
isolated daemon with a throwaway database:

- Page 1 returns **48 items** at `startLine: 6875`. It returned `unsupported` before.
- Page 2, anchored at `before=6875`, returns lines **6755–6872** — abutting exactly, with
  no overlap and no gap.
- The whole file parses to **2547 items**, with tool calls and their outputs paired exactly
  **1143 to 1143**.

29 new tests, each mutation-checked. Core suite: 1158 tests.

## Activating this

**Daemon-side** — this needs `dispatch update` (a rebuild and restart), not just a browser
refresh.

Watch one thing after updating: a Codex Pretty thread now builds its history from the
transcript rather than the socket replay, so its **open** path changed. Live turns still
stream over the socket as before.
